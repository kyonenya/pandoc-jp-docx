# Lua フィルター実行順序の設計メモ

## 概要

pandoc Lua フィルターを複数組み合わせるとき、フィルター同士の動作には依存関係が生じる。実行順を間違えると、ある入力で記号が欠落する／変換漏れが起きる、といった事故が静かに発生する。本プロジェクトでは経験的に発生した事故から、フィルターを 2 軸で分類して順序を決定する方針を採用している。

## 軸 1：入力堅牢性

> 自分のマッチ対象は、上流のフィルターが Str を分割した後でも生き残るか？

| 分類 | 性質 | 例 |
|---|---|---|
| **堅牢** | 単一文字のマッチ。Str がどれだけ細分化されても、どこかの Str 片に必ず残る | `str_rules` の `Str` パス（`§`/`′`/`″`/`(`/`)`） |
| **脆弱** | 複数文字のパターンマッチ。単一 Str 内に揃っている必要がある | `ruby` の `｜.-《.-》` |
| **普通** | コンテナ参照系。Str 分割そのものには強いが、`pandoc.utils.stringify` を呼ぶと RawInline の中身が落ちる | `str_rules` の `Strong` パス（内部で stringify） |

## 軸 2：出力礼儀

> 自分の出力は下流のフィルターにとって扱いやすいか？

| 分類 | 性質 |
|---|---|
| **destructive** | `RawInline('openxml', ...)` を生成して Str を壊す。下流に `stringify` 系・Str パターンマッチ系を置けない |
| **礼儀正しい** | Str を Str のまま残す。下流に何を置いてもよい |

## 順序ルール

1. **脆弱な系・`stringify` を呼ぶ系を上流に置く** — 自分のマッチが破壊される前に動かす
2. **堅牢な系を下流に置く** — 出力が destructive でも、入力が壊されにくいので位置自由度が高い
3. Div など他要素のみ扱うフィルターは、Inline 系列が終わった後ならどこでも安全

## 発生した事故

半角幅の固定（`Str` パス）を傍点（`Strong` パス）／`ruby` より先に動かしていたところ、`**日本§語**` の入力で § が消失した。原因：

1. 半角幅の固定が `Str "日本§語"` を `[Str "日本", RawInline(§), Str "語"]` に分割
2. 傍点の `pandoc.utils.stringify(elem.content)` が RawInline の中身（openxml 形式の生 XML）を「フォーマット情報」として捨てる。結果は `"日本語"`
3. 傍点はこの `"日本語"` を傍点 XML に包む。§ は完全に喪失

同様に、`ruby` の `text:match('(.-)｜(.-)《(.-)》(.*)')` は単一 Str 内に完全パターンがある前提なので、先に Str が分割されているとマッチ不能になりルビ未変換になる。

この事故は、両者を `str_rules.lua` に統合して `{ Strong = ... }` → `{ Str = ... }` の 2 パスに固定したことで構造的に起きなくなった。`Strong` パスは `stringify` した文字列を自前で run 分割するので、傍点の中でも § は保たれる。

## 循環依存：傍点 ↔ ruby

`str_rules` の `Strong` パスと `ruby` は互いに「自分が先に動きたい」要求を持つ：

- `ruby` は傍点が先だと困る（傍点が `Strong → RawInline` 変換で中身を消す）
- 傍点は `ruby` が先だと困る（`ruby` が `Str → RawInline` 化、`stringify` で中身が消える）

`**｜世界《せかい》**` のように Strong が ruby を丸ごと包むエッジケースは **どちらの順序でも壊れる**。

| 順序 | 壊れ方 |
|---|---|
| `傍点 → ruby` | ルビ記号 `｜《》` が生で表示される。**派手な失敗、校正で気づきやすい** |
| `ruby → 傍点` | ボールド／傍点が静かに落ちる。**地味な失敗、見落としやすい** |

このプロジェクトでは派手な失敗を選び、`傍点 → ruby` を採用している。

## walk と多重パスは依存性を解かない

pandoc の `elem:walk{...}` や、フィルターファイルが filter table の列（`return {{Note=...}, {Str=...}}`）を返して多重パスを表現する仕組みは、**1 つのフィルター内のスコープ制御や順序制御**には有効だが、**別ファイル間の CLI 順序の依存性**は変えない。

依存性の根本原因は `stringify` が RawInline を捨てること。これを構造的に消したい場合、`stringify` を呼ぶ filter を「子要素のうち Str は文字列化、RawInline はそのまま温存」と書き換える「RawInline 保持型」の実装に作り変える必要がある。本プロジェクトでは、`stringify` を呼ぶ傍点と、その中身を壊しうる半角幅の固定を同一ファイルに統合して順序を固定することで回避しているが、`ruby` のパターンマッチ脆弱性は残るため、順序ルールは不要になっていない。

## 新しいフィルターを足すとき

1. 入力堅牢性（単一文字 / 複数文字 / コンテナ参照）と、出力（destructive / 礼儀正しい）を分類する
2. 脆弱な系・`stringify` を呼ぶ系を上流、堅牢な系を下流に並べる
3. `defaults.yml` の `filters` を上記順序で並べる
4. 同じカテゴリ内で循環依存があるなら、どちらの壊れ方が校正で気づきやすいかで決める
